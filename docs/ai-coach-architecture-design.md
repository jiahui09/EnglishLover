> 状态：Active architecture baseline / 活跃系统架构基线  
> 最近刷新：2026-06-18  
> 文档定位：系统架构与目标技术架构基线，而不是 UI 架构、页面信息架构或代码实现方案。  
> 范围：EnglishLover AI Coach 从学习者体验、学习领域、目标技术架构、后端技术选型、AI 边界、数据证据、质量属性、多平台兼容到演进治理的整体系统架构。

## 0. 摘要

EnglishLover AI Coach 应被设计为一个**围绕每日学习闭环运行的英语学习系统**，而不是一组页面、一个 AI 生成器或一个背词工具的集合。

系统主线是：

```text
单词背诵 -> 阅读理解 -> 练习解析 -> 教练建议 -> 下一轮学习
```

本架构的核心结论：

1. **学习闭环是系统主架构**：所有能力都要服务“今日该学什么、当前怎么做、结果如何回流下一步”。
2. **领域边界先于技术边界**：先定义学习任务、阅读训练、作答解析、教练建议、学习画像、AI 降级等稳定业务边界，再决定后续实现形态。
3. **AI 是可替换的辅助能力，不是系统事实源**：AI 可生成内容和建议，但学习记录、作答事实、降级来源和建议依据必须可追溯。
4. **多平台共用一个学习模型**：移动端优先，平板 / 桌面 / Web 扩展空间与输入方式，但不拆成不同产品逻辑。
5. **性能、可靠性、可访问性和信任感是架构质量属性**：不是 UI 完成后的优化项，而是系统边界、状态流和降级路径的前置约束。

## 2. 外部架构理念与取舍

本设计参考了系统架构描述、软件架构视图、质量属性、领域建模、AI 风险治理、Flutter 多平台与性能等资料。取舍如下。

| 理念 / 框架 | 采用方式 | 在 EnglishLover 中的取舍 |
|---|---|---|
| ISO/IEC/IEEE 42010 架构描述 | 以 stakeholder、concern、view、rationale 组织架构 | 不只画结构图；必须说明学习者、产品、工程、运营等关注点，以及每个架构决策的理由 |
| C4 Model | 用 Context / Container / Component 的分层思维表达系统 | 本文只落到系统上下文与概念容器；不进入代码组件或具体服务实现 |
| arc42 | 用目标、约束、上下文、运行时、质量、风险组织文档 | 采用其结构化思路，但避免模板填空式冗长文档 |
| Well-Architected / 质量属性思想 | 将性能、可靠性、安全、可演进性作为架构目标 | 不以云厂商服务选型为中心，而转化为本项目可检查的质量场景 |
| DDD 领域驱动设计 | 按学习领域边界划分核心能力 | 避免按 UI 页面、数据库表或 AI prompt 组织系统模型 |
| AI 风险治理 | AI 输出需可解释、可降级、可追溯 | AI 不直接成为事实源；生成来源、失败状态、建议依据必须透明 |
| Flutter 架构与多平台原则 | 关注单一事实源、单向数据流、响应式与自适应 | 客户端共享学习模型，移动端优先，大屏增强而不改变业务逻辑 |
| WCAG / 包容性设计 | 把可访问性视为系统质量属性 | 低视力、键盘、触控、慢网络、AI 不可用都不是边缘情况 |

### 2.1 本项目采用的架构设计原则

1. **学习闭环优先**：系统以完成每日学习闭环为主线，功能不能脱离闭环自我膨胀。
2. **领域事实优先**：学习记录、作答、错因、建议依据是系统事实；UI 文案和 AI 输出只是事实的表达或辅助。
3. **AI 可替换、可降级、可追溯**：AI 能力不可用时，学习仍可继续；用户能知道内容来源与建议依据。
4. **客户端轻量且不中断学习**：首屏和主动学习不应等待远端或 AI；慢网、失败、离线要有可继续路径。
5. **多平台一致模型，自适应呈现**：不同设备调整布局与输入反馈，不改变学习状态机和领域语义。
6. **数据最小化与信任透明**：只收集支持学习反馈所需的数据；不把 mock、推断或 AI 生成伪装成真实历史。
7. **先边界、后拆分**：首版不追求微服务或复杂分布式形态；先稳定领域边界、质量门禁和演进方向。

### 2.2 明确拒绝的方向

- **页面拼装式架构**：把“今日 / 单词 / 阅读 / 教练”当成互不关联的页面集合。
- **AI 中心架构**：把系统价值押在一次生成成功上，失败后中断学习。
- **数据看板中心架构**：首版堆砌统计，而不是给出下一步学习行动。
- **平台分裂架构**：移动端、桌面端和 Web 各自形成不同学习逻辑。
- **过早技术拆分**：在领域模型和质量目标未稳定前引入复杂服务、队列、网关或云资源设计。

## 3. 利益相关者与架构关注点

| 利益相关者 | 主要关注点 | 架构回应 |
|---|---|---|
| 学习者 | 今天该学什么、能否不中断、反馈是否可信、是否有压力感 | 今日闭环、专注模式、降级阅读、私人教练式建议、透明来源 |
| 产品负责人 | 首版是否验证单词到阅读的学习价值 | 将学习闭环设为主架构，用完成率、建议可行动性和降级可用性做门禁 |
| 客户端工程 | 多平台如何共享逻辑、性能如何可控 | 单一学习模型、状态驱动 UI、移动优先、大屏增强、局部状态更新 |
| 后端 / 平台工程 | 边界如何划分、未来如何扩展 | 按学习领域和 AI 边界划分概念容器，不按页面或 prompt 直接建模 |
| AI / 内容负责人 | 生成质量、失败降级、来源透明 | AI 编排与内容降级分离，内容来源、生成依据和失败状态可追溯 |
| 数据 / 隐私负责人 | 学习数据如何最小化、如何避免误导 | 事实事件、派生画像、AI 输出分层；数据不足必须作为显式状态 |
| 运营 / 质量负责人 | 如何知道系统是否稳定、是否影响学习 | 观测闭环完成率、AI 降级率、错误率、慢路径、平台兼容问题 |

### 4.1 系统边界

EnglishLover 系统内部负责：

- 组织每日学习闭环；
- 管理单词训练、阅读训练、作答解析和教练建议的状态；
- 记录学习事实与必要证据；
- 调用或替换 AI / 内容能力；
- 在 AI、网络或数据不足时保持学习不中断；
- 为多平台提供一致体验；
- 收集足以保障质量的系统健康信号。

系统外部或暂不定义：

- 具体 AI 模型供应商；
- 云厂商和生产运行环境；
- 具体账号体系、支付体系、社区体系；
- 具体数据库 schema、迁移脚本、队列、网关或 API 字段；
- UI 组件设计细节。

## 5. 技术架构视图

EnglishLover 的首版技术架构采用“Flutter 客户端 + Go 模块化单体 API + PostgreSQL 事实源 + Redis 短期缓存 + AI 适配层 + OpenTelemetry 观测”的组合。目标不是先拆微服务，而是先把契约、事实源和降级路径稳定下来。

```text
Flutter 客户端
  -> HTTPS /api
Go API（模块化单体）
  - transport/http
  - application/usecase
  - domain
  - infrastructure/postgres
  - infrastructure/redis
  - ai/adapter
  - content/fallback
  - observability
PostgreSQL
Redis
AI providers / content sources
OpenTelemetry
```

### 5.1 前后端职责边界

| 层 | 选型 | 主要职责 | 明确不做 |
|---|---|---|---|
| Flutter 客户端 | Flutter + `ShadApp` + `ELTheme` | 页面呈现、专注模式、交互采集、弱网继续 | 不作为事实源，不直接写权威学习记录 |
| API 层 | Go `net/http` + 轻量路由 / 中间件 | 对外 HTTP 接口、鉴权、编排、状态机、契约响应 | 不把业务规则散落到 controller，不在此层直接持久化业务含义 |
| 应用层 | Go usecase / service | 学习流程编排、任务推进、AI 调用协调、降级决策 | 不耦合具体 UI，不知道页面结构 |
| 领域层 | Go domain | 学习事实、任务、会话、画像、建议语义 | 不依赖数据库表结构或第三方 API 形状 |
| 基础设施层 | PostgreSQL / Redis / AI adapter / OTel | 持久化、缓存、外部能力接入、观测 | 不承载领域规则 |

### 5.2 后端技术选型

| 决策 | 选择 | 理由 | 约束 |
|---|---|---|---|
| 服务形态 | Go 模块化单体 | 先把领域和契约稳定下来，避免微服务复杂度 | 后续可按边界拆分，但不作为首版目标 |
| 运行时 | Go 1.26 系列 | 与仓库现有目标线索一致，生态稳定，适合长期维护 | 版本升级需跟随项目统一决策 |
| HTTP 基础 | `net/http` | 标准库、可控、易测试、低锁定 | 若路由复杂度上升，再引入轻量路由层 |
| 数据库 | PostgreSQL 18 系列 | 适合作为学习事实源和关系型学习状态存储 | 只存权威事实，不存 AI 草稿当事实 |
| PostgreSQL 驱动 | `pgx/v5` | Go 生态成熟、能力完整、适合事务和类型映射 | 驱动选择须保持单一，避免双驱动并存 |
| 缓存 | Redis OSS | 适合短期状态、限流、幂等键、生成任务占位 | 不作为学习事实源 |
| 契约 | OpenAPI 3.1.2 | 让前后端和测试围绕同一接口契约协作 | 后端接口变更必须同步契约 |
| 观测 | OpenTelemetry | 统一 traces / metrics / logs，方便后续接入不同平台 | 不绑定单一可观测平台 |
| 日志 | `slog` | Go 标准日志，减少额外依赖 | 结构化字段需与 trace id 对齐 |
| AI 接入 | Provider adapter 层 | 保持模型 / 供应商可替换，统一降级语义 | 直接调用外部 AI 的代码不得散落在业务层 |

### 5.3 API 契约与接口边界

- API 统一通过 `/api/*` 暴露，由 Go API 提供 JSON 响应。
- OpenAPI 3.1.2 作为首版契约基线，前端、测试和后端围绕同一契约协作。
- 接口响应必须显式区分：
  - 用户学习事实；
  - 系统派生判断；
  - AI 生成内容；
  - 预置降级内容；
  - mock / 原型数据。
- 前端只消费契约，不反推事实；后端只返回来源明确的状态，不把推断写成事实。

### 5.4 典型请求链路

```text
用户完成单词反馈
  -> Flutter 客户端提交交互
  -> Go API 校验并写入学习事实
  -> PostgreSQL 成为权威记录
  -> Redis 仅承接短期状态与幂等控制
  -> 必要时调用 AI / 内容适配层
  -> 返回带来源标记的结果
  -> Flutter 按同一状态机渲染
```

### 5.5 部署与演进原则

- 首版只部署一个 Go API 服务、一个 PostgreSQL 实例、一个 Redis 实例和必要的 AI / 内容接入层。
- 背景任务可先用同一代码库中的 worker 入口承接，不预设多服务拆分。
- 微服务、消息总线和跨服务事务不是首版目标。
- 若后续边界稳定且负载需要，再按领域容器拆分，而不是按页面拆分。

### 5.6 概念容器视图

> “概念容器”表示系统职责边界，不等同于微服务、代码包或部署单元。

```text
学习者设备
  │
  ▼
[跨平台客户端]
  - 呈现今日任务、专注学习、阅读、解析和建议
  - 维护即时交互状态与弱网可继续体验
  - 不把 mock 或 AI 输出伪装成真实事实
  │
  ▼
[学习应用层]
  - 编排每日闭环与任务流转
  - 处理“下一步是什么”的应用状态
  - 隔离不同平台呈现差异
  │
  ▼
[学习领域层]
  - 单词训练
  - 阅读训练
  - 作答解析
  - 学习画像
  - 教练建议
  - 今日任务与闭环进度
  │
  ├──────────────► [AI 教练层]
  │                 - 阅读生成辅助
  │                 - 解析与建议辅助
  │                 - 生成依据、失败、重试、替换策略
  │
  ├──────────────► [内容与降级层]
  │                 - 预置阅读
  │                 - 题型与解析素材
  │                 - AI 不可用时的学习连续性
  │
  ├──────────────► [学习证据层]
  │                 - 学习事实
  │                 - 作答记录
  │                 - 来源标记
  │                 - 派生画像
  │
  └──────────────► [质量与治理层]
                    - 性能、错误、降级率
                    - 内容质量与安全信号
                    - 隐私、审计、可观测性
```

### 5.7 容器职责原则

- **跨平台客户端**关注即时体验，不承担长期事实仲裁。
- **学习应用层**关注流程编排，不直接内嵌 AI prompt、数据库结构或页面细节。
- **学习领域层**保存稳定业务语言，是系统长期可演进的核心。
- **AI 教练层**提供可替换能力，不覆盖学习事实。
- **内容与降级层**保障学习不中断，不把降级伪装成生成成功。
- **学习证据层**区分事实、推断、AI 输出和 mock。
- **质量与治理层**让性能、可靠性、隐私、安全和内容风险可观察。

## 6. 领域架构

### 6.1 核心域、支撑域与通用域

| 类型 | 领域 | 说明 |
|---|---|---|
| 核心域 | 每日学习闭环 | 决定产品差异化价值，连接单词、阅读、解析和建议 |
| 核心域 | 单词到阅读转化 | 把近期词、薄弱词转化为阅读材料与题目训练 |
| 核心域 | 教练建议 | 将学习证据转化为下一步行动，而不是只展示统计 |
| 支撑域 | AI 编排与降级 | 生成阅读、解析辅助、建议辅助，并在失败时回退 |
| 支撑域 | 学习画像 | 从学习事实派生掌握度、弱项和趋势摘要 |
| 支撑域 | 内容库 | 提供预置阅读、题型、解析与非 AI 兜底素材 |
| 通用域 | 用户与设备上下文 | 识别用户、设备、平台、输入方式与同步状态 |
| 通用域 | 观测、隐私与安全 | 支持系统健康、数据最小化、风险治理和审计 |

### 6.2 统一领域语言

后续任何实现、文案、接口或测试都应优先使用这些业务概念：

- 今日学习
- 单词训练
- 阅读训练
- 练习解析
- 教练建议
- 专注模式
- 近期词
- 薄弱词
- 目标词
- 预置阅读
- 学习画像摘要
- 数据不足
- AI 生成
- AI 降级
- 来源说明

### 6.3 领域状态分层

| 状态类型 | 示例 | 架构规则 |
|---|---|---|
| 学习事实 | 用户选择“认识 / 模糊 / 不认识”、提交答案、完成任务 | 必须可追溯，不由 AI 覆盖 |
| 派生判断 | 薄弱词、题型弱项、今日建议依据 | 必须能说明来自哪些学习事实 |
| AI 输出 | 生成阅读、解析辅助、建议草稿 | 必须标记来源、生成依据和失败 / 降级状态 |
| 呈现状态 | 加载中、错误、空状态、专注模式 | 可以因平台不同而变化，但不得改变学习事实 |
| mock / 原型数据 | 当前 `mock_learning_data` | 只能服务原型，不得被描述为真实历史或后端能力 |

## 7. 关键运行时视图

### 7.1 标准每日学习闭环

```text
进入今日学习
  -> 系统展示当前最小可行动任务
  -> 用户完成单词训练
  -> 学习事实记录近期词与掌握反馈
  -> 系统准备阅读训练
  -> AI 或预置内容提供阅读材料
  -> 用户阅读并作答
  -> 系统形成解析、错因和薄弱信号
  -> 教练建议给出下一步行动
  -> 今日状态回到首页形成闭环
```

架构要求：

- 首页不只是导航入口，而是闭环状态的投影。
- 单词、阅读、解析、建议必须共享同一条学习证据链。
- 用户可以跳过某些环节，但系统应说明学习收益与影响。

### 7.2 AI 生成失败或慢响应路径

```text
用户请求阅读训练
  -> 系统保留近期词与当前上下文
  -> AI 请求变慢或失败
  -> 用户看到可理解的等待 / 失败说明
  -> 系统提供重试或预置阅读
  -> 用户继续完成阅读和题目
  -> 教练建议标明本次内容来源
```

架构要求：

- AI 失败不是系统失败；学习闭环必须继续。
- 降级内容必须透明，不伪装成 AI 生成。
- 后续画像和建议必须知道本次训练基于生成内容还是预置内容。

### 7.3 弱网 / 离线可继续路径

```text
用户进入已可用任务
  -> 客户端保留必要上下文
  -> 网络变慢或不可用
  -> 用户仍可继续当前本地可用学习
  -> 新生成、同步或远端分析延后
  -> 恢复后再完成同步与状态校验
```

架构要求：

- 主动学习过程不应因暂时网络问题完全中断。
- 离线期间产生的学习事实必须与来源和时间保持可追溯。
- 若存在冲突，系统要保护学习事实，并向用户解释需要恢复的状态。

### 7.4 跨平台连续学习路径

```text
用户在移动端完成单词训练
  -> 学习事实进入权威状态
  -> 用户在桌面端继续阅读训练
  -> 桌面端根据同一学习模型展示更适合阅读的布局
  -> 解析与建议回流到同一今日闭环
```

架构要求：

- 不同平台可以改变布局和输入方式，不能改变领域语义。
- 大屏增强阅读与复盘，不新增与当前任务竞争的复杂入口。
- 专注模式在所有平台都应隐藏无关导航。

## 8. 数据与证据架构

### 8.1 数据分层

```text
原始学习事实
  -> 领域事件 / 状态
  -> 派生学习画像
  -> 教练建议与下一步任务
  -> 用户可见反馈
```

| 层级 | 内容 | 可信度与使用规则 |
|---|---|---|
| 原始学习事实 | 单词反馈、作答、完成状态 | 最高可信；用于回放和重新计算 |
| 领域事件 / 状态 | 今日任务进度、训练会话、阅读会话 | 应保持一致性；驱动页面和流程 |
| 派生画像 | 薄弱词、题型弱项、趋势判断 | 可重新计算；必须保留依据 |
| AI 输出 | 阅读、解析辅助、建议表达 | 需标记来源；不能覆盖事实 |
| 用户可见反馈 | 页面文案、建议、状态提示 | 必须区分事实、推断、AI 和降级 |

### 8.2 数据最小化

首版系统只应保留支撑学习闭环所需的数据：

- 今日任务状态；
- 单词接触与掌握反馈；
- 阅读内容来源；
- 题目作答与解析依据；
- 薄弱词和题型弱项；
- 教练建议依据；
- 必要的错误、性能和降级信号。

不应在没有产品价值和隐私说明的情况下扩张到重型画像、行为追踪或营销分析。

### 8.3 来源与可追溯性

所有影响用户理解和建议的内容都需要来源语义：

- 是用户真实完成的学习事实；
- 是系统从事实派生的判断；
- 是 AI 生成内容；
- 是预置阅读或降级内容；
- 是 mock / 原型数据。

这条规则是信任架构的一部分，不能被 UI 文案或实现便利性绕过。

## 9. AI 架构边界

### 9.1 AI 的角色

AI 在 EnglishLover 中承担三类辅助职责：

1. 根据近期词和薄弱词辅助生成阅读材料；
2. 根据作答和材料辅助组织解析；
3. 根据学习证据辅助表达教练建议。

AI 不承担：

- 学习事实仲裁；
- 无依据地生成学习画像；
- 静默改写用户记录；
- 在失败时阻断今日学习；
- 替代透明的内容来源说明。

### 9.2 AI 治理规则

- **输入可控**：AI 只能接收完成任务所需的最小学习上下文。
- **输出可标记**：生成阅读、解析、建议都要有来源语义。
- **失败可恢复**：失败、超时、内容不合格都应回到重试或预置阅读。
- **质量可评估**：阅读是否贴合近期词、题目是否可答、解析是否基于文本，需要进入后续质量门禁。
- **供应商可替换**：架构不绑定特定模型或平台。
- **用户可理解**：用户能知道“这是 AI 生成”“这是预置阅读”“这是基于你刚才的表现”。

## 10. 多平台兼容架构

### 10.1 平台策略

- **移动端优先**：服务碎片时间学习，强调单一主行动和低干扰。
- **平板 / 桌面增强**：提供更舒适的阅读、题目并排、复盘空间，但不改变学习模型。
- **Web 兼容**：优先保证可访问、可读、可键盘操作和弱网反馈，而不是追求复杂浏览器特性。

### 10.2 统一模型，不同呈现

```text
同一学习状态
  -> 移动端：单列、底部主行动、专注模式隐藏导航
  -> 平板：更宽阅读区、必要侧栏、仍保持当前任务优先
  -> 桌面 / Web：键盘与鼠标友好、阅读和题目可并列
```

### 10.3 输入与可访问性

系统应同时考虑：

- 触控目标与单手使用；
- 键盘焦点顺序；
- 鼠标 hover 不承载关键信息；
- 屏幕阅读器可理解进度、题目、反馈和降级说明；
- 减少动态效果；
- 安全区域、窗口尺寸变化和横竖屏变化。

## 11. 性能架构

### 11.1 性能目标

EnglishLover 的性能目标不是追求复杂跑分，而是保障学习连续性：

- 首页应快速回答“下一步做什么”；
- 主动学习不应被非必要远端请求阻塞；
- AI 等待要可理解、可取消或可降级；
- 阅读正文、题目和解析应保持稳定、低干扰；
- 弱网和失败状态不应让用户丢失学习进度。

### 11.2 架构级性能规则

- **首屏轻量**：首页展示今日任务不依赖 AI 现算结果。
- **状态局部化**：学习状态变化只影响相关区域，不造成整页无意义重建。
- **内容渐进可用**：已有单词、预置阅读和历史建议可先展示，生成结果后再更新。
- **长文本友好**：阅读正文、题目、解析的渲染要优先稳定排版和滚动流畅。
- **避免重型装饰依赖**：首版不应因图表、动画、字体或视觉特效牺牲学习速度。
- **感知性能明确**：加载、生成、同步、失败都要告诉用户系统正在做什么，以及用户还能做什么。

### 11.3 性能观测方向

后续实现应观测：

- 首页可用时间；
- 进入专注模式耗时；
- 阅读生成耗时与失败率；
- 预置阅读降级率；
- 阅读页滚动 / 输入卡顿；
- 跨平台布局异常；
- 学习事实保存失败或延迟。

本文不声明当前已有这些指标，只定义后续架构应观察的方向。

## 12. 可靠性、安全、隐私与可访问性

### 12.1 可靠性

- 学习事实优先保护，不能因 AI 失败、网络失败或页面切换丢失。
- AI 失败、内容不可用、数据不足、同步延迟都应是可表达状态。
- 预置阅读是主路径能力，不是临时错误页。

### 12.2 安全与隐私

- 只收集完成学习闭环所需的最小数据。
- 不把敏感学习记录发送给不必要的外部能力。
- AI 输入应控制上下文范围，避免无关个人信息进入生成链路。
- 用户可见建议不能夸大确定性，尤其在数据不足时必须说明。

### 12.3 可访问性

- 可访问性按系统质量属性处理，而不是 UI 末端修饰。
- 题目、反馈、进度、错误和降级说明必须有明确语义。
- 颜色不能单独承担正确 / 错误 / 警示语义。
- 键盘、屏幕阅读器、触控和减少动态效果都应进入后续验证。

## 13. 架构决策记录

### ADR-001：以每日学习闭环作为系统主架构

- 决策：所有系统能力围绕“单词 -> 阅读 -> 解析 -> 建议 -> 下一轮学习”组织。
- 理由：PRD 将首版成功定义为闭环可完成、任务清晰、反馈可行动、AI 失败仍可学习。
- 拒绝：页面集合架构、数据看板中心架构、AI 聊天中心架构。
- 风险：后续功能扩张可能稀释闭环；新增能力必须说明如何回流到今日学习。

### ADR-002：按领域边界建模，而不是按 UI、数据库或 prompt 建模

- 决策：稳定领域包括今日任务、单词训练、阅读训练、练习解析、学习画像、教练建议、AI 降级。
- 理由：UI 会迭代、AI prompt 会变化、存储技术会替换；学习领域语言更稳定。
- 拒绝：以页面名作为长期系统边界；以 AI prompt 结构作为系统事实模型。
- 风险：早期实现容易为了页面开发便利产生重复状态；需要质量门禁约束。

### ADR-003：AI 是可替换辅助层，不是系统事实源

- 决策：AI 输出必须与学习事实分层，并保留来源与降级语义。
- 理由：用户信任来自透明边界；AI 失败不能中断学习闭环。
- 拒绝：静默降级、全屏失败、把预置内容伪装成生成内容。
- 风险：如果来源语义缺失，画像和建议会误导用户。

### ADR-004：多平台共享学习模型，按平台自适应呈现

- 决策：移动、平板、桌面和 Web 共用同一领域模型和状态流。
- 理由：学习闭环不应因设备变化而分裂；Flutter 适合用同一代码基础做响应式和自适应。
- 拒绝：为桌面端另建复杂学习路径，或让 Web 只成为缩水版。
- 风险：大屏增强可能重新引入干扰；专注模式规则必须跨平台保留。

### ADR-005：选择 Go 模块化单体作为首版后端形态

- 决策：首版后端采用 Go 模块化单体，而不是 Firebase/BaaS、Node 全栈或微服务。
- 理由：仓库 CI 与部署模板已经预留 Go 后端线索；Go 适合长期维护、清晰边界和可部署 API。
- 拒绝：过早微服务、把后端职责交给 BaaS、在没有工程基线前切换 Node 全栈。
- 风险：如果模块边界不受约束，单体仍会退化为大泥球；需要用领域层、OpenAPI 契约和测试门禁约束。

### ADR-006：选择 PostgreSQL 作为学习事实源

- 决策：学习事实、任务状态、作答记录、来源标记和派生画像的权威存储使用 PostgreSQL。
- 理由：EnglishLover 的核心数据是可追溯学习事实和关系型学习状态，需要事务、一致性和长期可维护性。
- 拒绝：Redis 作为事实源、客户端本地状态作为权威事实、AI 输出直接写成真实历史。
- 风险：后续 schema 设计必须保留事实 / 推断 / AI 输出 / 预置内容 / mock 的分层，否则会损害信任架构。

### ADR-007：选择 Redis 作为短期缓存和运行时辅助，不作为事实源

- 决策：Redis 仅用于短期缓存、限流、幂等键、生成任务占位和可恢复运行时状态。
- 理由：AI 生成与弱网体验需要短期状态，但学习事实必须落到 PostgreSQL。
- 拒绝：把学习进度、作答记录或画像只放在 Redis。
- 风险：缓存与事实源可能出现不一致；实现时必须以 PostgreSQL 回放和校验为准。

### ADR-008：选择 OpenAPI 契约优先组织前后端协作

- 决策：Go API 的 `/api/*` 接口以 OpenAPI 3.1.2 作为首版契约基线。
- 理由：当前产品和客户端原型已经明确页面与学习流程，但后端尚未落地；契约优先能让前端、后端和测试共享边界。
- 拒绝：前端直接按 mock 数据结构推进、后端先写接口再补文档。
- 风险：契约如果只描述字段而不描述来源语义，仍会产生“AI / 预置 / 事实”混淆；接口必须携带来源和降级状态。

### ADR-009：AI 接入采用 Provider-neutral Adapter

- 决策：AI 阅读生成、解析和建议通过可替换 adapter 接入，不在业务层绑定具体供应商。
- 理由：PRD 要求 AI 失败仍能学习；架构必须允许重试、降级、内容质检和供应商替换。
- 拒绝：把 prompt、供应商 SDK 或模型参数散落在 usecase / handler 中。
- 风险：adapter 抽象过早复杂化会拖慢首版；首版只抽象生成、解析、建议、失败、来源和降级这些必要能力。

## 14. 架构质量门禁

后续任何功能、文档或实现切片都应通过下列门禁。

| 门禁 | 必须回答的问题 |
|---|---|
| 闭环一致性 | 改动是否支持单词、阅读、解析、建议的学习闭环？ |
| 领域一致性 | 是否使用统一领域语言，避免页面局部私有状态？ |
| AI 透明度 | AI 生成、降级、失败、数据不足是否对用户透明？ |
| 学习事实保护 | 用户学习事实是否可追溯、可保存、不会被 AI 覆盖？ |
| 性能 | 首页、专注模式、阅读和 AI 等待是否保持学习不中断？ |
| 多平台 | 移动、平板、桌面、Web 是否共享模型并适配输入方式？ |
| 可访问性 | 键盘、触控、屏幕阅读器、对比、减少动态效果是否可检查？ |
| 隐私 | 是否只使用完成学习闭环所需的最小数据？ |
| 可观测性 | 失败、降级、慢路径和学习完成情况是否可被后续观察？ |
| 验证 | 是否有文档检查、内容审查、测试或手工检查证据？ |

## 16. 使用与推广条件

本文可作为 EnglishLover 后续系统设计、实现计划和质量审查的基线，但使用时必须遵守：

- 不把本文当作已完成的后端实现；实现前仍需单独设计 API 字段、数据库 schema、部署脚本、测试和迁移计划。
- 不把当前 Flutter mock 原型描述为真实后端、AI 或同步能力。
- 所有新能力必须回到每日学习闭环，说明服务哪一个学习状态。
- 所有 AI 用户可见行为必须有来源、失败和降级表达。
- 所有平台共享同一学习模型；平台差异只体现在布局、输入和可用性增强。
- 文档、代码和测试都必须保留“事实、推断、AI 输出、mock”的边界。
